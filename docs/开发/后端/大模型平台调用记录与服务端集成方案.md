### 多模态内容类型标识

请求中的`type` 是多模态内容类型标识（Discriminator），用于告诉 API 当前传入的是文本、图片、视频还是音频；`text` 则是 `type: "text"` 对应的内容字段。它们是 OpenAI 兼容协议规定的字段，不能随意改名，但 `type` 可以使用不同的枚举值。

阿里云百炼的 Chat Completions 接口支持以下内容类型：

| type          | 对应内容字段  | 用途                   |
| ------------- | ------------- | ---------------------- |
| `text`        | `text`        | 传入普通文本           |
| `image_url`   | `image_url`   | 传入图片 URL 或 Base64 |
| `video_url`   | `video_url`   | 传入视频文件           |
| `video`       | `video`       | 传入视频帧列表         |
| `input_audio` | `input_audio` | 传入音频数据           |

注意，并不是所有模型都支持全部类型。当前使用的 `qwen3.8-flash` 支持文本、图片、视频输入，输出文本；不支持音频输入。如果需要音频理解，可以考虑 `qwen3.8-omni-flash`。

#### 不同类型的 JSON 写法

普通文本

```
{
  "type": "text",
  "text": "你好，请介绍一下自己"
}
```

图片

```
{
  "type": "image_url",
  "image_url": {
    "url": "https://example.com/image.png"
  }
}
```

视频文件

```
{
  "type": "video_url",
  "video_url": {
    "url": "https://example.com/video.mp4",
    "fps": 2
  }
}
```

视频帧列表

```
{
  "type": "video",
  "video": [
    "https://example.com/frame1.jpg",
    "https://example.com/frame2.jpg"
  ]
}
```

音频（需使用支持音频的模型）

```
{
  "type": "input_audio",
  "input_audio": {
    "data": "data:audio/wav;base64,...",
    "format": "wav"
  }
}
```

上述是不同模态的字段结构，具体是否可用由模型能力决定。

**纯文本可以简化，不必指定 type**

对于纯文本请求：

```
{
  "role": "user",
  "content": "你好，请介绍一下自己"
}
```

等价于：

```
{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "你好，请介绍一下自己"
    }
  ]
}
```

只有需要混合文本、图片等不同模态时，才通常使用 `content` 数组。

#### 与 Responses API 的区别

OpenAI 还有另一套 `/responses` 接口，其类型命名不同：

| Chat Completions | Responses API |
| ---------------- | ------------- |
| `text`           | `input_text`  |
| `image_url`      | `input_image` |

两种接口不能直接混用参数格式。百炼也提供了相应的 Responses 兼容协议。

对于你现在的 `qwen3.8-flash` 调用，推荐继续使用 `/chat/completions`，图片用 `image_url`，文字用 `text`。 这是标准且兼容性较好的写法。

## 对话

如果是开发普通 AI 聊天功能，那么 Chat Completions 更合适。

但如果你要开发的是类似 Codex 的 Agent 系统，涉及工具调用、结构化事件、代码修改和模型推理过程管理，那么 Responses API 值得考虑。

DeepSeek 的 Responses API 是无状态的，不会像 OpenAI 的部分 Responses API 用法那样在服务端保存会话。 因此，并不是选了 Responses API，就自动获得服务端对话记忆。

## Chat Completions 和 Responses

### 区别

| 对比维度       | Chat Completions API            | Responses API                      |
| -------------- | ------------------------------- | ---------------------------------- |
| 请求地址       | `/chat/completions`             | `/responses`                       |
| 请求结构       | `messages`                      | `input`、`instructions`            |
| 响应结构       | `choices[].message`             | `output[]`                         |
| 普通文字聊天   | 支持                            | 支持                               |
| 多轮对话       | 客户端维护历史                  | 客户端维护历史                     |
| 流式输出       | SSE，`data: [DONE]` 结束        | SSE，语义化事件结束                |
| 思考模式       | `thinking` / `reasoning_effort` | `reasoning.effort`                 |
| 图片理解       | 支持                            | 支持，具体内容类型受限             |
| 工具调用       | Function Calling                | Function、特定 Custom Tool         |
| 结构化输出     | JSON Object                     | JSON Object、JSON Schema           |
| 内置网络搜索   | 无统一内置搜索工具参数          | Pro 模型支持 `web_search`          |
| Spring AI 集成 | 原生 DeepSeek ChatModel         | 需要确认对应 SDK／适配器支持       |
| 适合场景       | 聊天、问答、RAG、常规 Agent     | Codex 类 Agent、复杂工具及事件编排 |

Spring AI 已提供官方 DeepSeek 模型 Starter：

```
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-deepseek</artifactId>
</dependency>
```

配置示例（以 Spring AI 2.0.2 文档为准）：

```
spring:
  ai:
    model:
      chat: deepseek
    deepseek:
      base-url: https://api.deepseek.com
      api-key: ${DEEPSEEK_API_KEY}
      chat:
        model: deepseek-flash
```

这个 Starter 使用 DeepSeek 的 `/chat/completions` 接口，支持普通对话、流式输出、工具调用和思考模式。

对于 Java 后端项目，使用 `ChatClient` 或 `DeepSeekChatModel` 就能接入，不必自行实现 Responses API 的事件解析。

### 选型

| 你的实际需求                       | 建议接口         |
| ---------------------------------- | ---------------- |
| 普通 AI 聊天页面                   | Chat Completions |
| 流式聊天、历史消息管理             | Chat Completions |
| Spring AI + RAG 知识库             | Chat Completions |
| Spring AI + Function Calling Agent | Chat Completions |
| Codex 类代码 Agent、`apply_patch`  | Responses        |
| DeepSeek Pro 内置 Web Search       | Responses        |

> **什么时候值得选择 Responses API？**
>
> Responses API 并非单纯的下一代聊天接口。
>
> DeepSeek 官方明确表示，它新增该格式的重要原因是适配 Codex。
>
> 尤其当你需要以下能力时，它更有价值：
>
> - 结构化事件流： 区分模型推理、文本生成、工具参数增量等事件。
> - 更丰富的工具输出： 支持 `function_call` 和面向代码修改的 `apply_patch`。
> - 内置网页搜索： `deepseek-v4-pro` 可以通过 `web_search` 工具直接搜索。
> - JSON Schema： 支持使用指定 Schema 约束结构化响应。
>
> 但这里有个重要限制：DeepSeek 的 Responses API 不支持 `previous_response_id`、`conversation`、`store` 和 `background`，这些参数即便传入，也不会获得对应的服务端能力。

## Chat Completions API

### Anthropic 格式与 OpenAI 格式的区别

DeepSeek 官方目前同时兼容三套常见接口协议：

| 协议                    | 路径                     | 主要兼容生态                   |
| ----------------------- | ------------------------ | ------------------------------ |
| OpenAI Chat Completions | `/chat/completions`      | OpenAI SDK、Spring AI DeepSeek |
| Anthropic Messages      | `/anthropic/v1/messages` | Anthropic SDK、Claude Code     |
| OpenAI Responses        | `/responses`             | OpenAI Responses SDK、Codex    |

其中 Anthropic Messages API 是为了兼容 Anthropic 生态而提供的。它不是另一个独立的 DeepSeek 模型服务。

### 区别1：请求参数

| 维度           | Chat Completions                           | Anthropic Messages                           |
| -------------- | ------------------------------------------ | -------------------------------------------- |
| 请求路径       | `/chat/completions`                        | `/anthropic/v1/messages`                     |
| 认证方式       | `Authorization: Bearer`                    | `x-api-key`                                  |
| 模型字段       | `model`                                    | `model`                                      |
| System Prompt  | `messages` 中的 `system`                   | 顶层 `system`                                |
| 用户消息       | `messages`                                 | `messages`                                   |
| 最大输出 Token | `max_tokens`                               | `max_tokens`                                 |
| 流式响应       | `stream: true`                             | `stream: true`                               |
| 响应内容       | `choices[].message.content`                | `content[]`                                  |
| 流式事件       | `data` 增量、`[DONE]`                      | `message_start`、`content_block_delta` 等    |
| 工具调用       | `tool_calls`                               | `tool_use`                                   |
| 工具结果       | `role: tool`                               | `tool_result` 内容块                         |
| 思考模式       | DeepSeek 的 `thinking`、`reasoning_effort` | Anthropic 风格的 `thinking`、`output_config` |

DeepSeek 对 Anthropic 的兼容并非百分之百。例如 Anthropic 的 `mcp_servers` 会被忽略，`thinking.budget_tokens` 也会被忽略。

### 区别2：请求方式

方式 A：Chat Completions

推荐普通聊天

```
curl -sS -N \
  https://api.deepseek.com/chat/completions \
  -H "Authorization: Bearer ${DEEPSEEK_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-flash",
    "messages": [
      {
        "role": "system",
        "content": "你是一个Java开发助手"
      },
      {
        "role": "user",
        "content": "你好"
      }
    ],
    "thinking": {"type": "disabled"},
    "stream": true
  }'
```

方式 B：Anthropic Messages

推荐 Anthropic SDK

```
curl -sS -N \
  https://api.deepseek.com/anthropic/v1/messages \
  -H "x-api-key: ${DEEPSEEK_API_KEY}" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "deepseek-flash",
    "max_tokens": 1024,
    "system": "你是一个Java开发助手",
    "messages": [
      {
        "role": "user",
        "content": "你好"
      }
    ],
    "stream": true
  }'
```

这两个请求的目标都是让 `deepseek-flash` 回答「你好」。

实际区别在于请求格式与响应解析，而不是选择了两种不同的模型。

### 区别3：流式输出格式

这是实际开发中最需要关注的差异。

Chat Completions：

```
data: {"choices":[{"delta":{"content":"你好"}}]}

data: {"choices":[{"delta":{"content":"！"}}]}

data: [DONE]
```

主要从 `choices[0].delta.content` 读取文本增量。思考模式下还可以读取 `reasoning_content`。

DeepSeek API Docs



Anthropic Messages：

```
event: content_block_start
data: {"type":"content_block_start",...}

event: content_block_delta
data: {"type":"content_block_delta","index":0,
"delta":{"type":"text_delta","text":"你好"}}

event: message_stop
data: {"type":"message_stop"}
```

Anthropic 的 SSE 是结构化事件流，会区分消息开始、内容块增量和消息结束等阶段。

上面均为简化示意，省略了部分字段和事件。

如果你要自己实现 HTTP 客户端，两者需要不同的事件解析逻辑；如果使用 SDK，通常由 SDK 处理这些差异。

### 区别4：接口功能

不能简单认为 Anthropic Messages 比 Chat Completions 更先进，或者反过来。

两者支持的核心能力高度重合：

| 能力                                | Chat Completions | Anthropic Messages |
| ----------------------------------- | ---------------- | ------------------ |
| 文本生成与对话                      | 支持             | 支持               |
| SSE 流式输出                        | 支持             | 支持               |
| 多轮会话                            | 支持             | 支持               |
| 思考模式                            | 支持             | 支持               |
| 图片理解                            | 支持             | 支持               |
| Function / Tool Calling             | 支持             | 支持               |
| DeepSeek Flash / Pro                | 支持             | 支持               |
| 与 Claude Code 直接集成             | 非原生协议       | 直接兼容           |
| 与 Spring AI DeepSeekChatModel 集成 | 直接支持         | 非该适配器的协议   |

这里有一个容易混淆的问题：

协议兼容不代表完全支持原始平台所有能力。

例如，DeepSeek 的 Anthropic API 虽然兼容 `tool_use` 和 `tool_result`，但它不等于完整的 Claude 平台服务，也不能直接获得 Anthropic 所有服务端工具和基础设施能力。

同理，Chat Completions 也不代表只能做普通聊天。它同样可以实现支持工具调用和多轮交互的生产级 Agent。

### 结合 Spring AI，怎么选？

你现在的目标是 Java 后端统一接入大模型，使用 Spring AI 开发聊天和 Agent 功能。

Spring AI 官方的 `DeepSeekChatModel` 实现直接使用 `/chat/completions`，提供同步 `call()` 和流式 `stream()` 两套接口。

例如：

```
@RestController
@RequestMapping("/ai")
public class ChatController {

    private final ChatModel chatModel;

    public ChatController(ChatModel chatModel) {
        this.chatModel = chatModel;
    }

    @GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> chat(@RequestParam String message) {
        return chatModel.stream(message);
    }
}
```

这里的 `stream()` 实际通过 DeepSeek 的 Chat Completions 流式 API 获取响应，再通过 Spring WebFlux 的 `Flux` 推送给客户端。

Spring AI 会处理底层 HTTP 流式响应，你不用手动解析 SSE，也不需要考虑 curl 的 `-N`。

| 开发场景                          | 推荐               |
| --------------------------------- | ------------------ |
| Java + Spring AI 普通聊天         | Chat Completions   |
| Java + Spring AI 流式聊天         | Chat Completions   |
| Java + Spring AI + RAG / Agent    | Chat Completions   |
| Claude Code 使用 DeepSeek         | Anthropic Messages |
| Anthropic SDK 应用迁移到 DeepSeek | Anthropic Messages |
| Codex / OpenAI Responses SDK      | Responses API      |

> 看来还是OpenAI格式略胜一筹。

# 如何在服务端管理模型

目前Spring AI框架支持多模型的调用配置，但需要区分“模型能力支持”和“多模型配置管理”两件事。

截至 2026 年 10 月 29 日，Spring AI 最新稳定版为 2.0.2，已经提供聊天、向量、多模态视觉和图片生成等模型能力的统一抽象。不过，Spring AI 并不是一个开箱即用的多模型注册中心。

## Spring AI 版本兼容关系

| Spring Boot       | 建议 Spring AI 版本 |
| ----------------- | ------------------- |
| Spring Boot 3.5.x | Spring AI 1.1.8     |
| Spring Boot 4.x   | Spring AI 2.0.2     |

Spring AI 2.x 对配置项和底层 OpenAI SDK 有较大调整，因此以下的 YAML 是按 2.0.2 编写的，不应直接照搬到 1.1.x。

## Spring AI 支持情况

| 模型类型            | Spring AI 接口             | 支持情况 |
| ------------------- | -------------------------- | -------- |
| 文本模型            | `ChatModel` / `ChatClient` | 原生支持 |
| 向量模型            | `EmbeddingModel`           | 原生支持 |
| 视觉理解模型        | `ChatModel` + `Media`      | 原生支持 |
| 文生图模型          | `ImageModel`               | 原生支持 |
| 图文生图 / 图片编辑 | `ImageModel` + 厂商扩展    | 需要适配 |

其中最容易混淆的是：

- 视觉理解不是独立的 `VisionModel`。它属于多模态 Chat，使用 `UserMessage` 传入文字和图片。
- 文生图属于 `ImageModel`，与 Chat 是不同的模型接口。
- 图文生图没有完全统一的跨厂商调用规范。尤其是百炼的 `qwen-image-3.0`，虽然使用 OpenAI 兼容路径，却需要额外传入 `image` 字段。

目前测试的百炼模型，可以这样对应：

| 百炼模型                  | Spring AI 使用方式           |
| ------------------------- | ---------------------------- |
| `qwen3.8-flash` 文本生成  | `ChatModel`                  |
| `qwen3.8-flash` 图片理解  | 同一个 `ChatModel`           |
| `qwen3.7-text-embedding`  | `EmbeddingModel`             |
| `qwen-image-3.0` 文生图   | `ImageModel`，需验证兼容行为 |
| `qwen-image-3.0` 图文生图 | 单独适配图片输入             |

## 如何配置多类大模型配置

以 Spring AI 2.0.2 + Spring Boot 4.x 为例，一个 OpenAI Starter 就可以同时提供 Chat、Embedding 和 Image 的自动配置。

### Maven 依赖

```
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>2.0.2</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-starter-model-openai</artifactId>
    </dependency>
</dependencies>
```

### application.yml

```
spring:
  ai:
    model:
      chat: openai
      embedding: openai
      image: openai

    openai:
      base-url: https://ws-xuj64ag8x47upqti.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
      api-key: ${DASHSCOPE_API_KEY}

      # 文本生成 + 视觉理解
      chat:
        model: qwen3.8-flash

      # 向量模型
      embedding:
        model: qwen3.7-text-embedding
        dimensions: 1024
        encoding-format: float

      # 文生图模型
      image:
        model: qwen-image-3.0
        size: 1024x1024
```

上述配置项来自 Spring AI 2.0.2 官方文档，其中 `chat.model`、`embedding.model`、`image.model` 都可以分别设置。

另外，2.0.2 的 OpenAI 集成已经使用官方 `openai-java` SDK，因此这里的 Base URL 包含 `/compatible-mode/v1`，不要再手工拼接 `/v1`。

这样会形成三个不同职责的模型客户端：

## 如何配置单类多种大模型

Spring AI 默认的自动配置主要提供每种模型类型的默认实例，而不是下面这种无限扩展的命名模型清单：

```
# 示例：不是 Spring AI 原生识别的多模型配置格式
spring:
  ai:
    models:
      - name: qwen3.8-flash
      - name: qwen-plus
      - name: deepseek-v3
```

但可以通过运行时参数切换同一提供商、同一兼容协议下的模型。

例如：

```
String result = chatClient.prompt()
    .user("你好")
    .options(OpenAiChatOptions.builder()
        .model("qwen-plus")
        .build())
    .call()
    .content();
```

这不需要创建一个新的 `ChatModel`，只是在调用时覆盖默认模型。

如果切换的是不同厂商、不同 API Key、不同 Base URL，则需要配置多个客户端实例，或者实现模型连接管理。

## 如何兼容需要适配的大模型

比如图文生图现在，SpringAI框架还不兼容百炼的格式，是需要特别处理的部分。

百炼的 `qwen-image-3.0` 使用的是：

```
POST /compatible-mode/v1/images/generations
```

图文生图通过请求体扩展字段实现：

```
{
  "model": "qwen-image-3.0",
  "prompt": "将这张图片转换成日系插画风格",
  "image": "https://example.com/input.png"
}
```

但 Spring AI 的标准 `ImagePrompt` / `OpenAiImageOptions` 主要覆盖文本提示词、模型、图片数量、尺寸等参数，并没有对应百炼这个扩展 `image` 字段的标准配置。

因此建议：

- 文本、向量、视觉理解：优先使用 Spring AI 原生接口。
- 纯文生图：优先测试 `ImageModel` 的兼容性。
- 图文生图：使用 Spring `RestClient` 或已有 HTTP 组件封装百炼专属调用，不强行套入不完整的通用接口。

## 未来的模型管理策略

可以考虑把 Spring AI 作为调用框架，把实际模型清单维护在独立配置中。

例如：

```
ai:
  models:
    - id: qwen3.8-flash
      provider: bailian
      capabilities:
        - CHAT
        - VISION

    - id: qwen3.7-text-embedding
      provider: bailian
      capabilities:
        - EMBEDDING

    - id: qwen-image-3.0
      provider: bailian
      capabilities:
        - IMAGE_GENERATION
        - IMAGE_EDIT
```

注意，这只是建议的业务层配置结构，不是 Spring AI 自带的配置属性，需要你自己的模型注册与路由逻辑来解析。

这样比把每个模型都注册成独立 Spring Bean 更适合动态模型管理，但对于当前只有三四个模型的场景，没必要一开始就增加注册中心。
